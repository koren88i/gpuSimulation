What is this page?

This page compares two ways to use the same total number and type of GPUs for the same model and workload: one larger deployment, or several independent copies of a smaller measured deployment.

  1. Start with measured results. We use recorded InferenceX operating points and only pair deployments with equal GPU budgets and a shared workload profile.
  2. Build the split baseline. We take one measured smaller deployment and multiply its throughput or session capacity by the number of independent copies that fit in the same GPU budget. Per-request latency is not multiplied.
  3. Compare like with like. The percentage shows the difference between the selected larger point and the combined split baseline. Both sides use the same planning assumptions.

Why these five by default? They are a small, source-checked editorial set chosen to make the report approachable and show different models, hardware layouts and outcomes. They are examples—not the five biggest wins and not a statistical sample. Use the Collection menu to explore all 15 latency-qualified comparisons or all 318 generated records.

How to read the result: it describes selected measured points, not proven maximum capacity. A larger deployment can win or lose, and software differences or sparse load sweeps may help explain the result.

Changing these assumptions scales session and DAU estimates; it does not change their relative advantage.

ⓘ Reserve: meaning & default

The fraction of observed session capacity held back from the user estimate. More reserve reduces both sessions and DAU. Default: 20%, an illustrative headroom allowance for variability. It is not a measured safety margin or an availability guarantee; lowering modeled occupancy does not remeasure latency.

ⓘ Active hours: meaning & default

Total time each daily user occupies a root coding session, summed across the day. It includes the session's recorded pauses and subagent activity, not just GPU generation time or time logged in. Default: 2 hours, an illustrative part-day coding-agent usage scenario. It is not an average measured from users. More hours per user means fewer DAU for the same concurrent capacity.

ⓘ Activity window: meaning & default

The span of the day over which the modeled population's usage is concentrated. Default: 8 hours represents one workday in a common time zone, an illustrative scenario rather than a measured traffic pattern. A wider window supports more DAU at the same peak capacity and peak ratio. It does not mean each user is active for eight hours.

ⓘ Peak ratio: meaning & default

Peak concurrent occupancy divided by average concurrent occupancy within the activity window. Default: 2 means the busiest time has twice the window's average load, an illustrative allowance for uneven demand. No production traffic trace establishes this value. A higher peak ratio lowers DAU. Reserve separately holds capacity back; this ratio describes when demand occurs.

How these inputs become sessions and DAU

The workload is grounded in AgentX; the numeric usage defaults are planning assumptions. They were not fitted to measured human usage and are not an established “typical coding user” profile. The defaults describe a part-day user population sharing one workday, with uneven demand and spare capacity.

S = C × (1 − r) ÷ R

DAU = S × W ÷ (H × P)

C is the selected benchmark's configured root-session concurrency; r is reserve as a fraction; R is root sessions per active user; S is estimated supported concurrent active users. W is the activity window in hours, H is active session-hours per daily user, and P is the within-window peak ratio.

Why this equation: DAU × H gives daily user-hours. Dividing by W gives average simultaneous users; multiplying by P gives peak simultaneous users. Set that peak equal to S and solve for DAU. This is an occupancy estimate, not a count of completed tasks or a forecast of adoption.

Fixed mapping: R = 1. One root session tree represents one active user, the simplest explicit mapping. AgentX subagents belong to that tree; they are not extra human users. Multiple independent root sessions per person would reduce supported user counts. The UI keeps this mapping fixed.

Same treatment on both sides: calculate the larger point from its measured C. For k independent smaller copies, calculate one smaller point and multiply sessions and DAU by k. Apply identical usage inputs. These controls do not reselect benchmark points.

Eligibility defaults: p90 first-token latency ≤ 10 seconds and p90 time per output token ≤ 100 ms. These are illustrative responsiveness ceilings, not user-validated service targets. Both required metrics must be present and pass. They are fixed in this UI. Fixed-length tests have no coding-session/DAU estimate under the default profile.
